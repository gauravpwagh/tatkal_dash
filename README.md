# Tatkal Booking Reform -- Analysis Dashboard

A small interactive tool for comparing Indian Railways' current Tatkal
booking system against a proposed "computerized random allotment" system,
across revenue, system overhead, and how many applicants actually get a
shot at a seat -- including a scenario where post-reform demand rises
while seat capacity stays fixed.

A key distinction the tool draws out: under today's system, "not getting
a ticket" can mean two very different things -- not being allocated a
seat after getting into the booking process, or being locked out of
the process entirely because the infra couldn't absorb the burst load.
The proposed system is modelled as always letting everyone in (see
[§3.2](#32-scenarios)).

This accompanies the earlier discussion/report on reforming Tatkal
booking (FCFS randomness, computerized random allotment, blocked-payment
settlement, flat processing fee + reduced premium financing model). The
tool operationalizes that proposal's numbers so they can be explored
interactively rather than read as static tables.

## 1. Quick start

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
streamlit run tatkal_dashboard.py
```

This opens a local browser tab (default `http://localhost:8501`) with
three tabs: **Inputs**, **Scenario comparison**, **Export report** (a
landscape-A4 PDF with every input, the comparison table, the comparison
charts, and tier-level detail).

No external services, API keys, or network access are required -- it is
a fully offline, single-process app.

**Number formatting:** all INR figures use Indian digit grouping
(`₹1,32,25,000`, not `₹13,225,000`), and net revenue is additionally
shown in lakhs (`₹132.25 L/day`) since that's the unit these numbers are
naturally discussed in.

## 2. File layout

```
tatkal_dashboard/
├── tatkal_model.py       # Pure-Python calculation engine (no UI code)
├── tatkal_dashboard.py   # Streamlit UI -- imports tatkal_model
├── requirements.txt
└── README.md             # this file
```

**Why the split?** `tatkal_model.py` has zero dependency on Streamlit.
You can `import tatkal_model` from a unit test, a Jupyter notebook, a
Flask/FastAPI backend, or a batch script, and get the exact same numbers
the dashboard shows. If you rebuild the frontend in React/Next.js later,
only `tatkal_dashboard.py` needs to be replaced or ported -- the model
module is the part worth keeping stable.

`tatkal_dashboard.py` also owns PDF generation: `matplotlib` renders the
comparison charts as images and `reportlab` assembles the PDF (with
DejaVu Sans registered so the ₹ sign renders -- the standard PDF
Helvetica font has no glyph for it). Both are pure-Python, no system
binary (e.g. `wkhtmltopdf`) required.

## 3. The model, in plain terms

### 3.1 Tiers

Demand and fares are modelled per fare **tier** (default: Non-AC,
Mid-AC, Upper-AC -- edit or add/remove rows freely in the Inputs tab).
Each tier carries:

| Field | Meaning |
|---|---|
| `seats_per_day` | Tatkal seats available per day (fixed capacity) |
| `requests_per_day` | booking requests/applications per day (demand) |
| `avg_base_fare` | average base fare for the tier, INR |
| `current_surcharge_pct`, `current_min_charge`, `current_max_charge` | today's Tatkal surcharge: `pct * base_fare`, clipped to `[min, max]` |
| `proposed_flat_fee` | flat, non-refundable processing fee, paid by every applicant |
| `proposed_premium_pct`, `proposed_min_premium`, `proposed_max_premium` | reduced premium paid only by successful applicants, same clip logic |

### 3.2 Scenarios

Three scenarios are computed from the same tier inputs:

- **A -- Current system** (`compute_current`): access is gated by infra
  capacity *before* seat allocation even runs. `capacity_pct =
  current_infra_cost_per_day / current_infra_required_cost_per_day`
  (capped at 100%) caps what share of `requests_per_day` can get into
  the process at all; the rest are `denied_access` -- turned away by an
  overloaded system, never competing for a seat. Of those who get in,
  successful bookings = `min(seats, accessible_requests)`, and the
  remainder are `unsuccessful` (not allocated a seat due to ordinary
  scarcity). These are two distinct failure modes, surfaced separately
  everywhere in the UI -- see [§3.2.1](#321-two-ways-to-not-get-a-ticket).
  Revenue = successful bookings x current surcharge. Overhead = flat
  infra cost (the *actual* spend, not the capacity-100% figure) + cost
  of failed payment attempts generated by the *seat lock-and-release
  cycle* (see `lock_release_multiplier` below).

- **B -- Proposed system, same demand** (`compute_proposed`, multiplier
  `1.0`): access is **not** gated -- the whole point of spreading intake
  over an extended window instead of a single burst is that everyone
  gets in (`denied_access` is always 0). Successful applicants are still
  capped at `seats_per_day`. Every applicant pays the flat fee; only
  successful applicants also pay the reduced premium. Overhead = flat
  (lower) infra cost + verification cost x total applications +
  refund/release cost x unsuccessful applicants.

- **C -- Proposed system, demand surge** (`compute_proposed`, multiplier
  = user-set slider, default `3.0x`): identical formula to B, but
  `requests_per_day` is multiplied by the surge factor while
  `seats_per_day` is **not** -- modelling "more people apply because
  entry is now cheap and low-risk, but capacity is unchanged." This is
  the scenario that stress-tests whether flat-fee revenue growth
  outpaces verification/refund-processing overhead growth as volume
  rises.

All three scenarios return a `ScenarioResult` with `.net_revenue`
(`revenue - overhead`), `.access_denied_pct`, `.seat_allocation_denial_pct`,
and `.denial_rate_pct` (the sum of the two -- kept for anyone who wants
the combined figure, though the dashboard and PDF report now surface the
two components directly instead) computed as properties, so adding a new
metric only requires adding one property to that class.

#### 3.2.1 Two ways to not get a ticket

The tool deliberately keeps these separate rather than folding them into
one "denial rate," because they call for different fixes:

- **Denied access (locked out)** -- never got into the process at all.
  Only possible under Current; driven by infra capacity vs. demand (see
  `current_infra_required_cost_per_day` below). The fix is infra
  investment or -- what the Proposed system actually does -- redesigning
  intake so a burst-capacity investment isn't needed in the first place.
- **Unsuccessful (lost seat)** -- got into the process, but wasn't
  allocated a seat due to ordinary scarcity (more requests than seats).
  Possible under every scenario; the only fix is more seats or less demand.

The illustrative defaults make this concrete: Current spends the same
₹15L/day on infra as Proposed, but because Current needs to absorb an
instantaneous burst while Proposed spreads intake over a window, Current
can only let in 30% of demand (₹15L / ₹50L required) while Proposed lets
in 100% at the same spend.

### 3.3 Overhead assumptions (system-wide, not per-tier)

| Field | Meaning |
|---|---|
| `current_infra_cost_per_day` | actual amount spent on infra for today's burst window |
| `current_infra_required_cost_per_day` | what it would cost to give every applicant access during the burst (100% capacity); the gap between this and actual spend drives `denied_access` |
| `lock_release_multiplier` | average number of lock/payment attempts per confirmed seat under the current system (>1 models the repeated seat lock-and-release cycle from the technical report) |
| `payment_failure_cost` | support/reconciliation cost per failed payment attempt |
| `proposed_infra_cost_per_day` | cost of provisioning for a smoothed extended-window arrival pattern -- always 100% capacity by design, see §3.2.1 |
| `verification_cost_per_application` | identity + fraud-screening cost, charged once per application regardless of outcome |
| `refund_processing_cost_per_unsuccessful` | cost of releasing a block / refunding one unsuccessful applicant |

All defaults (`default_tiers()`, `default_overhead()` in
`tatkal_model.py`) are **illustrative placeholders**, loosely anchored to
figures discussed in the accompanying report (~1.5 lakh total Tatkal
seats/day, tiered surcharge structure, etc.) but not verified current
IRCTC data. Treat every number in the UI as editable, not authoritative.

## 4. Extending the tool

Some natural next steps, roughly in order of effort:

1. **Per-tier overhead** -- currently overhead assumptions are global;
   splitting `OverheadAssumptions` per tier (e.g. AC classes may have
   costlier verification) is a small refactor of the same dataclass
   pattern.
2. **GST handling** -- add an optional GST% field to fees/premiums and
   apply it in the revenue calculation, matching the 18% GST on
   processing fees and 5% GST on AC-class fares discussed in the report.
3. **Monte Carlo arrival simulation** -- replace the deterministic
   `min(seats, requests)` success rule with a simulated draw over a
   modelled arrival-time distribution, to explore fairness/variance
   questions rather than just aggregate totals. `numpy.random` is enough;
   no new architecture needed, just a new function alongside
   `compute_current`/`compute_proposed`.
4. **Sensitivity / what-if sweep** -- wrap `run_all_scenarios` in a loop
   over a parameter range (e.g. `surge_multiplier` from 1x to 10x) and
   plot net revenue vs. multiplier, to find the break-even point where
   overhead growth catches up with fee revenue growth.
5. **Persistence** -- save/load named input sets (e.g. as JSON) so
   different policy scenarios can be stored and reloaded; `TierInput`
   and `OverheadAssumptions` are plain dataclasses, so
   `dataclasses.asdict()` + `json.dump` gets you most of the way there.
6. **Swap the frontend** -- because `tatkal_model.py` has no Streamlit
   imports, a FastAPI wrapper exposing `run_all_scenarios` as a JSON
   endpoint, consumed by a React frontend, is a straightforward next
   step if this needs to move beyond a local analyst tool.

## 5. Known simplifications (be aware of these before presenting results)

- Successful bookings are always `min(seats, requests)` -- i.e. the tool
  assumes capacity is always the binding constraint when
  `requests > seats`. It does not model partial seat wastage (unsold
  Tatkal berths) or class-substitution effects.
- The "lock-and-release" overhead model in the current system is a
  simple multiplier, not a queueing simulation; it captures the *shape*
  of the effect described in the report, not a validated cost estimate.
- Infra capacity is modelled as a straight-line ratio (`actual spend /
  required spend`, capped at 100%), not a real queueing or load-testing
  model -- it captures the *shape* of "underfunded burst infra locks
  people out" without claiming a specific spend level maps to a specific
  access percentage in reality.
- Demand in Scenario C scales uniformly across tiers by a single
  multiplier; in reality different fare tiers would likely see different
  elasticity to a lower-cost, lower-risk entry fee.
- No time-of-day or route-level granularity -- all figures are
  daily national aggregates by tier.

These are exactly the kind of gaps flagged in the accompanying report's
"Limitations" section as needing real data (an RTI reply, a pilot, or
load-testing) before the numbers should inform an actual funding or
policy decision. This tool is for exploring the *shape* of the trade-off,
not for producing a defensible forecast.
